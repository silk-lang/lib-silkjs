## What is new in the design

- **Trusted element accesses** (`ssa_opt_hoist`, code-quality.md "Array checks in front of the
  loop"). One `check.array` per Array in front of a loop; the accesses (`Inst.trusted`) test
  only the index and leave past the count. A failed check on a baseline frame is remembered
  under the header's pc with `ssa.SITE_ARRAY` (through `jit_exit_state.CODE_ARRAY_CHECK` in the
  exit record), and the next compile trusts nothing in that loop but keeps its other hoisting.
- **Eight integer registers on a baseline frame** (`x64_regalloc.framePool`). rsi, rdi, rdx,
  r10 and rcx are fragile: a value takes one only if every instruction of its interval keeps
  them (`keepsFragile`). Exits now take how they left in r8, not rcx. Any lowering change
  that touches rsi, rdi, rdx, r10 or rcx in an instruction `keepsFragile` names breaks values
  silently: keep that list and the lowering in step.
- **Loops in one piece** (`Function.compact`, `loopDepths`). The block order puts a loop's
  blocks right after its header; before, a latch could land after the rest of the function,
  which made every carried value's interval huge.
- **Parameter writes in inlined bodies** (`ssa_translate`, `Translator.paramWrites`,
  inlining.md). They write the caller's operand in `held`; every exit after one leaves with
  the bodies' frames. This is what lets Crypto's am3 inline.
- **Backend details** worth knowing when reading machine code: `mul.i32`'s -0 test and the
  trusted accesses' slow paths are out of line after the blocks (`zeroInsts`, `coldPieces`); a
  trusted store reuses the element address a read of the same element left in R11
  (`reusesElement`); compares reuse flags and RAX (`flagsHold`, `raxHolds`).
- A verifier refusal with `--jit-dump` prints the SSA and where the check failed
  (`jit: unverified ssa`, `jit: verify: block ... inst ... value ...`). Refusals that are not
  limits of the subset are compiler bugs; the eight benchmarks currently show none.

## How changes were checked

Every commit passed, with the release shell built from it:

1. `silk test --timeout 900 --no-cache` in `modules/jit` (101 tests).
2. The 69 scripts in `modules/jit/tests/baseline` giving the interpreter's output under
   `--jit-opt`, `--jit-baseline`, `--jit --jit-calls` and `--jit-opt=5 --jit-threshold=5`.
3. The eight V8 benchmarks printing their `done` lines under `--jit-opt=20 --jit-threshold=20`,
   with and without `--jit --jit-calls`.
4. For a change meant to keep the code the same: identical machine code. Run the old and new
   shell under `setarch -R` with `--jit-dump` and compare the bytes of the
   `jit: optimized code at` lines.

`--jit-stress` refuses optimized code on a baseline frame (`x64_backend.supported`), so it
tests nothing in frame mode; the low thresholds in step 2 replace it.

## Measuring on a noisy VM

- The VM has no hardware counters. Instruction counts (callgrind) are stable; the clock moves
  by 5 to 10% between runs of the same build. Register-to-register moves are nearly free on
  the clock: count fewer memory trips and taken jumps, not only instructions.
- Crypto seeds its random numbers from the clock, so its instruction count varies by up to 8%
  between runs of one build. For instruction counts prepend
  `Date.prototype.getTime = function () { return 1234567890123; };` to the timed script.
- `modules/jit/prof/bench/ab_shells.py SCRIPT SHELL...` interleaves shells on one core and
  prints medians and minimums: the way to tell two builds apart (15 rounds or more).
- `modules/engine/scripts/jit_hot.py --flags=--jit-opt --blocks N` gives the per-instruction
  profile of compiled code. Its block names are the bytecode prefixes; map them to functions
  with the `jit: optimizing` lines of its dump (the `jit: hot` line follows each).

## Next

The next goal was set but not started: **RayTrace's optimizer at or under 1,100 ms at scale 20**
(at least 2x the interpreter; now 2,234 against the interpreter's 2,215 and V8's 314). Start
with `jit_hot.py` on RayTrace, look at what is refused or left (`--jit-dump`: `jit: refused`,
`jit: left`, `not inlined`), and at whether its doubles stay boxed.

Left in Crypto, by size: field reads in inlined bodies that stay owned because the borrow pass
works within one block (`x.array`, `r.array` in every inlined am3 call, with their counts and
releases); the method closure an inlined known call still materializes and counts; compiling
(about 13% at scale 20: 98 compiles, bnpDivRemTo 8 times, each learning one site).

The HTTP order service is still slower under the optimizer than the interpreter;
`handoff-2026-11-21.md` ("Update, evening of 22 November") has the instruction-fetch finding.

Julia's rules and the way she wants updates reported are in `handoff-2026-11-21.md`, "Julia's
rules" and "How to report updates". She asked for this branch's PR and will continue elsewhere.
