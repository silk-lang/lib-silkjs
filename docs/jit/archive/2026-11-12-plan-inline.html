A JIT compiler for SilkJS

Reach V8 and JSC on peak throughput, and pass them on warmup, latency, memory and startup, while the engine keeps building and running with no JIT at all.

The gap to close is entirely in optimized code. The SilkJS interpreter already runs at the level of V8's interpreter; V8's optimizing compilers are what put it 8.5 times ahead on the V8 benchmark suite.

Goal and win conditions

Two fixed constraints

  • The JIT is optional. The engine stays embeddable without it, including on WebAssembly, and the interpreter-only build must not get slower or larger.
  • Better, judged by measurement. Every design choice is settled by throughput, warmup, latency and memory. Mechanisms from V8 and JSC are adopted where they pay and left out where they are legacy.

What counts as winning

  • Peak throughput: at or above V8 and JSC on the geometric mean of Octane and JetStream-class suites, with no single test more than about 1.3 times behind.
  • Time to peak: ahead of both, by starting from persisted profiles and code.
  • Pause time and peak memory: ahead of both.
  • Startup: keep the current lead.

Beating both engines on every benchmark is not something this plan promises. Their top tiers are near the state of the art for generic JavaScript, so parity on peak speed is the realistic target and the lead comes from the other three lines.

Where we can lead

V8 and JSC are built for browsers: untrusted code, one-shot page loads, phone memory limits. SilkJS serves a Node-compatible runtime, where code is trusted, long-lived and run again on every start.

  1. Warmup. Persist type profiles and compiled code beside the existing code cache, so the second run of a program starts at peak speed.
  2. Whole-program knowledge. The ES module graph is static. The compiler can inline across modules and treat never-reassigned exports as constants, invalidated the same way shapes are.
  3. Latency and memory. Reference counting frees memory at once and has no collection pauses. Tail latency and peak memory become headline metrics.
  4. The runtime boundary. Node pays for each crossing between JS and C++. The runtime's native calls can be declared to the compiler with types and effects, so hot ones (buffers, streams, fs) are called directly or inlined.
  5. Hindsight. Start from the designs both engines reached after rewrites: a control-flow-graph SSA IR, data-driven inline caches, two architectures from the first day, fuzzing before features.

What the engine gives us today

Already fits a JIT

  • Shapes carry versions and a runtime-wide epoch, which is the invalidation signal compiled code needs.
  • The dispatch loop exists in two copies (plain and observed) with a handoff between them. Deoptimization uses the same mechanism.
  • The Exception value tag gives helper calls a plain C-ABI error return.
  • Heap cells never move, so compiled code can hold raw pointers.
  • Silk has extern "C", inline assembly and native C sources.
  • The interpreter is a complete oracle for differential testing.

Needs work

  • Reference counting. Each value copy writes memory; compiled code must avoid most of those writes.
  • 16-byte values. ValueBits is a tagged union, twice a NaN-boxed word. NaN-boxed property slots were tried and reverted (#779, #802).
  • Caches keyed by site in side tables. The compiler needs per-function feedback at stable addresses, covering arithmetic types, call targets and element kinds as well as shapes.
  • No hotness counters and no executable-memory manager yet.

Design

Packaging

  • The JIT is a third package, modules/jit, depending on the engine by path as the runtime does. The engine never imports it.
  • The engine exposes one seam: a hotness counter and a native-entry slot per function, behind a hook that is a type parameter. With no JIT linked it folds away, like PlainRun and ObservedRun.
  • Engine-side changes must speed up the interpreter on their own. Feedback vectors qualify because they replace the site-keyed cache tables.

Execution tiers

  • Interpreter, unchanged in role, collecting feedback.
  • One optimizing compiler with two effort levels: a quick mode for functions that have just become hot, and a full mode for those that stay hot.
  • No separate baseline JIT. If the warmup curve later shows a gap between interpreter and quick mode, a tier is added then.

Compiler

  • One SSA IR over a control-flow graph, built from bytecode and feedback by abstract interpretation of the operand stack.
  • Speculation on shape, int32, double, call target and array element kind, each guarded by a check that deoptimizes.
  • Deoptimization rebuilds interpreter frames at a bytecode boundary and continues in the interpreter. There is one target, so one frame-reconstruction path.
  • Inline caches are data in the feedback vector, read by interpreter and compiled code alike. Machine code is written once and never patched, which keeps pages write-xor-execute.
  • Invalidation by shape epoch and by module-export assumptions.
  • One macro assembler for x86-64 and arm64, shared with the regexp compiler.
  • Compilation runs on a background thread; the main thread installs finished code at a safe point.
  • Hot builtins such as map and forEach are written in JS so ordinary inlining optimizes them through the callback.

Memory model open, decided in Phase 1

Three candidates, compared on throughput, pause time and peak memory:

  • Reference counting with compiler elision. Values in registers are borrowed; counts change only at heap stores and escapes. Least change.
  • Reference counting with an uncounted nursery. Young objects are bump-allocated and not counted until they escape. Published work on this family (LXR, PLDI 2022) reports beating production tracing collectors on both latency and throughput.
  • A tracing collector. The highest known ceiling for allocation-heavy code, and the largest rewrite. It cannot scan the stack on WebAssembly, so that build would need precise roots.

NaN-boxing values to 8 bytes is evaluated alongside, after reading why the earlier attempt was reverted.

Phases

Durations assume the current pace of agent-driven work with the stress harness in place. Parity on Octane-class peak speed at 12 to 18 months is ambitious and not guaranteed.

Phase 0

Measure

1 week
  • Install Silk dev.69, build head, and re-run every number on this page.
  • Add d8 and jsc as comparison columns in scripts/v8bench.py and scripts/bench.py.
  • Add JetStream and the Web Tooling Benchmark.
  • Build the scorecard: throughput, time to peak, p99 pause, peak memory, startup, binary size.

Done when one command prints the scorecard for SilkJS, Node, d8 and jsc, and the result is recorded in bench/results.

Phase 1

Seam and feedback

2 to 3 weeks
  • Per-function feedback vectors; move the field caches into them; add arithmetic, call-target and element-kind feedback.
  • Hotness counters on function entry and loop back-edges.
  • The tier hook and the empty modules/jit package.
  • Executable-memory manager: write-xor-execute, MAP_JIT on macOS, cache flush on arm64, code freed with its bytecode.
  • The verification harness (see below).
  • One week of memory-model experiments, ending in a decision.

Done when the interpreter-only build is no slower and no larger, test262 matches the same 19 known failures, and the memory model is chosen.

Phase 2

Compiler, quick mode

2 to 3 months
  • Macro assembler for x86-64, then arm64.
  • SSA construction from bytecode and feedback.
  • Type and shape speculation with deoptimization to interpreter frames.
  • Linear-scan register allocation.
  • Reference-count elision, or the chosen memory model's equivalent.
  • Background compilation.
  • Opcode coverage grows by measured heat; uncovered opcodes keep the function in the interpreter.

Done when Richards, DeltaBlue, Crypto and NavierStokes are 3 to 5 times faster than the interpreter, on both architectures, with the stress modes and fuzzer clean.

Phase 3

Compiler, full mode

4 to 6 months
  • Inlining, including polymorphic sites and JS-written builtins.
  • Unboxed int32 and double values in registers.
  • Load elimination, global value numbering, loop-invariant code motion.
  • Range analysis and bounds-check elimination.
  • Escape analysis and scalar replacement.
  • Loop entry by on-stack replacement.
  • Declared native calls for the runtime's hot paths.
  • Generators and async functions in compiled code.

Done when the geometric mean on Octane and JetStream-class suites is within 1.3 times V8 and JSC.

Phase 4

Lead

ongoing, starts during Phase 3
  • Persist profiles and compiled code in the code cache; compile hot functions at load.
  • Cross-module inlining and constant exports.
  • Close remaining single-test gaps from the scorecard.

Done when a restarted server reaches peak throughput in its first second, and the scorecard leads on time to peak, pause and memory.

Verification

The compiler has no reference implementation to translate, so correctness rests on these checks. They are built in Phase 1, before any code is generated.

  • Tier-forcing flags: interpreter only, compile everything on first call, quick mode only, full mode only.
  • Deopt stress: every speculation check fails on a schedule, so each deoptimization point is exercised.
  • Memory stress: collection or count verification at every allocation.
  • test262 per tier configuration, against the same 19 known failures as today.
  • The runtime's Node compatibility suite under the compile-everything flag.
  • Differential fuzzing with Fuzzilli: interpreter result against compiled result.
  • Performance gate: the scorecard runs on every JIT change; the interpreter-only build is one of its columns.

Risks and unknowns

  • Scale. V8 and JSC each hold hundreds of engineer-years. Agents make breadth cheap (two architectures, 256 opcodes, test triage). Rare deoptimization and memory bugs are the hard part, and only the harness finds them.
  • Reference-counting ceiling. If the chosen memory model keeps counts, allocation-heavy code may stop short of V8. The Phase 1 experiments are there to find this early.
  • Security. A JIT is new attack surface. Write-xor-execute pages and fuzzing are in from Phase 1.
  • Interpreter stays first-class. WebAssembly builds cannot JIT, and debugging and coverage run in the observed loop.

Not yet verified

  • Whether Silk can call into a raw executable buffer with a custom calling convention. If not, it needs a small compiler feature or a C shim.
  • Why NaN-boxed property slots were reverted in #802.
  • How head compares with the 6 November build measured here.
  • Any JSC numbers.
